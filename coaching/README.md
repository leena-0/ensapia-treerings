# 코칭 카드 (Coaching Cards)

팀원들의 업무일지를 분석해서, 팀 리더(1차평가자)가 놓치기 쉬운 구조적 문제(병목, 방치된 요청 등)와
눈에 띄지 않은 성과를 격주로 카드 형태로 알려주는 기능. `구현명세_코칭카드.md`(v10.2 확정) 스펙의
실제 구현체.

## 1. 핵심 설계 원칙

> **AI가 하는 일**: 분류·대조·계수·추출 (탐지 대상을 찾아내고, 근거를 뽑아내고, 점수를 계산)
> **AI가 하지 않는 일**: 판단·평가·추정 (이게 진짜 문제인지, 얼마나 심각한지는 코드가 정한다)

이 원칙이 파이프라인 전체를 관통한다:

- **탐지·근거검증·점수·확신도·선별·(카드/긴급 분리)는 전부 코드**(결정론, 재현 가능, 테스트 가능).
- **LLM은 딱 한 곳에만 쓰인다**: 이미 확정된 근거를 자연스러운 한국어 문장으로 서술하는 것
  (`nodes.generate_card_text`). LLM 응답이 근거를 뒷받침하지 못하면(`grounded: false`) 그 카드는
  통째로 버려진다.
- LLM 없이도 전체 파이프라인이 100% 동작한다(`--no-llm`, 코드 템플릿으로 서술). 탐지·선별 결과는
  LLM 유무와 무관하게 항상 같다 — 서술 문장만 달라진다.

왜 이렇게 만들었는지는 실제로 겪은 문제 때문이다: 초기엔 "대기 대상 정규화"(표현이 다른 병목을
같은 것으로 묶는 작업)까지 LLM에 맡겼는데, 당사자 1명을 빠뜨리는 recall 문제가 실측으로 나왔다.
그래서 탐지를 전부 코드로 옮기고, LLM은 서술만 하도록 좁혔다.

## 2. 파이프라인 구조 (LangGraph)

```
                    ┌─→ detect_bottleneck ──┐
                    ├─→ detect_unresolved ──┤
START → collect ────┼─→ detect_rework ──────┼─→ merge → verify → confidence → score → select → generate → split_urgent → END
                    ├─→ detect_load ────────┤
                    └─→ detect_unrecognized ┘
```

- **라우터(조건 분기) 없음.** "어떤 탐지기를 켤지"는 실행 중 분기가 아니라, `build_graph(enabled_detectors=...)`
  호출 시점에 그래프에 어떤 노드/엣지를 추가할지로 결정된다(기본은 5종 전부).
- **fan-out/fan-in**: `collect`에서 활성 탐지기 전부로 병렬 분기하고, 전부 끝나야 `merge`로 모인다.
  탐지기들은 서로 다른 state 키(`*_candidates`)에만 쓰므로 충돌하지 않는다.
- **confidence가 score보다 먼저다** — v10.2 점수식이 확신도 항을 쓰기 때문(`score_and_rank`).
- 파일 구성: `graph.py`(그래프 조립·`run_coaching()` 진입점) / `nodes.py`(각 단계 실제 로직) /
  `data_adapter.py`(CSV 목데이터 → 스키마 변환) / `schemas.py`(pydantic 모델) /
  `store.py`(인메모리 저장소) / `api.py`(FastAPI).

## 3. 탐지 유형 5종

| 유형 | 코드 함수 | 대상 인원 | 핵심 로직 |
|---|---|---|---|
| **의존 병목** dependency_bottleneck | `detect_bottleneck` | 2명 이상 | `reports/coaching_signals.py`의 "대상 토큰" 군집화 재사용 — "막혔을 때만 언급되는 단어"로 2명 이상이 같은 대상을 기다리는지 판정 |
| **미해결 요청** unresolved_request | `detect_unresolved` | 1명 | 요청 마커 있고 이후 "해결" 마커가 **같은 내용 토큰 2개 이상 겹치며** 나오지 않으면 후보 |
| **재작업 반복** rework_loop | `detect_rework` | 1명 | 수정/롤백/재작업 마커가 한 사람에게 3건 이상 |
| **부하 편중** load_imbalance | `detect_load` | 1명 | 로그 수가 팀 평균×1.6 **그리고** 평균+3 모두 충족 |
| **미인지 성과** unrecognized_work | `detect_unrecognized` | 1명 | 성과 마커 있는 문장(위험/부정 표현 없이) 2건 이상, 반복 보고는 중복 제거 |

병목만 여러 명이 될 수 있고(구조적으로 여러 사람을 동시에 막을 수 있는 유일한 유형), 나머지 4종은
항상 1명이다 — 그래서 뒤에 나올 확신도 규칙상 병목만 "high"까지 갈 수 있다.

### 3-1. 의존 병목 탐지의 함정 — "대상 토큰"이 진짜 어려운 부분

핵심 아이디어는 단순하다: 병목의 대상(예: "리워드 구성안")은 **막혔을 때만** 언급되고 평상시
진척 로그에는 안 나온다. 그래서 "대기 로그에는 2건 이상 등장하되 비대기 로그에는 전혀 안 나오는"
단어만 "대상 토큰"으로 인정한다(`reports/coaching_signals.py::_object_tokens`).

문제는 이 배타성 기준을 만족하는 게 대상 명사만이 아니라는 것. 실측으로 발견한 과결합 사례들:

- "이슈"/"발생"/"일부" 같은 막연한 사건 서술어
- "있음"/"없어"/"나서"/"보류함"/"전이라"/"재요청"/"가능"/"정하고"/"요청함"/"다음" 같은 문장
  종결·연결 일반어 — 대기 상황을 서술할 때 거의 항상 붙어서, 완전히 무관한 병목 두 개를 이 단어
  하나로 묶어버린다.
- "기다리는"/"늦어지고"/"밀리는" 같은 상태 동사의 활용형 — 마커 자체(`대기`/`지연`)는
  불용어 처리돼 있어도, 그 동사의 다른 활용형은 정확 일치가 아니라서 안 걸린다.

`reports/coaching_signals.py`의 `_STOPWORDS`/`_MARKER_PREFIXES`가 이런 케이스를 계속 추가해온
결과물이다. **이건 근본적으로 대상(명사)과 상태(동사/어미)를 구분 못 하는 어휘 기반 휴리스틱의
구조적 한계**라서, 데이터가 늘어날수록 새로운 충돌이 나올 수 있다(§8 참고).

## 4. 근거 검증 (`verify_evidence`, LLM 절대 개입 안 함)

```python
valid = [e for e in c["evidence"]
         if e["message_id"] in text_by_id and e["excerpt"] in text_by_id[e["message_id"]]]
```

두 가지를 코드로 대조한다: ① `message_id`가 실제로 존재하는가, ② `excerpt`가 원문의 **부분 문자열**로
그대로 들어있는가. 유효 근거가 2건 미만이면 카드 자체를 폐기한다. LLM이 근거를 지어내거나 살짝
바꿔 쓰는 걸 코드가 기계적으로 걸러내는 마지막 방어선.

## 5. 우선순위 점수 (v10.2 확정 공식)

```
점수 = 유형기본값 × 확신도 × 영향범위 × 지속계수 × 채택률보정
```

| 인자 | 값 |
|---|---|
| 유형기본값 | 의존 병목 1.0 / 미해결 요청 0.9 / 나머지 0.8 |
| 확신도 | high 1.0 / medium 0.6 (low는 애초에 생성 안 됨) |
| 영향범위 | 1명 0.5 / 2명 0.8 / 3명 이상 1.0 |
| 지속계수 | `0.5 + 0.5 × min(1, 지속일수/10)` (하한 0.5, 상한 1.0, 10일 포화) |
| 채택률보정 | `max(0.3, (채택+1)/(채택+기각+2))` — 라플라스 평활, 이력 없으면 0.5 |

확신도(§6): 명시적 근거 3건 이상 **그리고** 영향 2명 이상이면 high, 근거 2건 이상이면 medium,
그 외는 카드를 만들지 않는다(low는 생성 자체가 안 됨). 이 조건 때문에 병목만 high가 될 수 있다
(나머지 4종은 영향범위가 항상 1명).

## 6. 선별 — 슬롯 분리

점수 상위 5건을 그냥 뽑지 않고 **문제 슬롯(최대 4)** 과 **인정 슬롯(최대 1)** 을 나눠서 채운다
(`select_top_n`). 미인지 성과는 영향범위가 항상 1명(계수 0.5 고정)이라 단일 순위로 세우면 3명짜리
병목에 밀려 영원히 선별되지 않기 때문이다. 인정 후보가 없는 주기엔 문제 카드로 빈 슬롯을 채운다.

## 7. 배치 vs 즉시(`split_urgent`)

- **긴급 조건**: `영향 3명 이상 AND 지속 5일 이상`, 또는 **문제 카드**에 릴리스/납기 키워드
  ("릴리스"/"출시"/"납기"/"배포"/"장애"/"긴급")가 근거에 포함.
- 릴리스 키워드 체크는 문제 카드에만 적용한다 — 인정 카드가 "배포 완료"처럼 좋은 소식에 같은
  단어를 써도 긴급으로 잘못 튀지 않게 하기 위함(실측으로 발견하고 고친 버그, §8 참고).
- 조건을 만족하면 격주 배치에서 빠져서 **즉시 DM 경로**(`urgent_alerts`)로 간다. 3명짜리 병목이라도
  지속이 짧으면(예: 3일) 카드로 남는다 — affected와 duration 둘 다 필요하다.

## 8. LLM 서술 (`generate_card_text`)

- 프롬프트(`CARD_TEXT_PROMPT`)는 근거·유형·인원·지속일만 넘기고, 확신도별로 **body의 마지막
  문장이 반드시 만족해야 할 형식**을 지시한다:
  - high: "(행동)하시면 (결과)됩니다." 형식의 실행 가능한 조언 문장으로 끝나야 함
  - medium: "...확인이 필요해 보입니다" 류의 질문형으로 끝나야 함, 단정 금지
  - (튜닝 전엔 "조언 문장으로 써라"는 느슨한 권고였는데, high 카드 8건 중 1건만 지킴 → 마지막
    문장 형식을 못 박은 뒤 8건 중 8건으로 개선됨. 실측 확인.)
- `card_type`은 내부 식별자(`rework_loop` 등 snake_case)를 절대 그대로 프롬프트에 넣지 않는다 —
  `CARD_TYPE_LABEL_KO`로 한국어 라벨("재작업 반복")로 바꿔서 넣는다. 넣지 않으면 일부 LLM(Solar
  Pro)이 그 식별자를 그대로 베껴 써서 리더가 읽을 문장에 코드명이 노출된다(실측 확인, 수정됨).
- `res.get("grounded") is False`면 그 카드는 버려진다.
- **미인지 성과 카드의 톤은 아직 미해결 과제**: 좋은 소식인데도 medium 확신도라 "확인이 필요해
  보입니다"로 끝나서 걱정하는 것처럼 들린다. 별도 프롬프트가 필요하지만, "애매한 칭찬글을 AI가
  분류해야 하는 부담"이 있어서 의도적으로 보류 중이다.

### 프로바이더 (`reports/llm_client.py`)

`LLM_PROVIDER` 환경변수로 선택(기본 `upstage`=Solar Pro 3, `gemini`로 되돌릴 수 있음).
litellm 기반이라 프로바이더 교체가 모델 문자열 하나 바꾸는 것으로 끝난다. 기본값을 Gemini에서
Solar Pro로 바꾼 이유: Gemini 무료 티어가 **일일 요청 20건 한도**라 대량 배치 테스트(8사이클×3건
=24회)조차 못 끝내는 걸 실측 확인했다. Solar Pro는 같은 배치를 대기 없이 완주했다.

## 9. 데이터 스키마 (`schemas.py`)

- **입력**: `WorkLog`(업무일지 1건), `WeeklyStatusSelection`(본인이 고른 주간 상태 — AI가 "정체"를
  자동 판정하지 않고, 본인이 `blocked`로 표시한 것만 코칭 후보가 되게 하는 입력원), `TeamContext`.
- **출력**: `CoachingCard`(headline/body/confidence/evidence/priority_score 등), `Evidence`
  (message_id/permalink/excerpt — excerpt는 항상 원문 부분 문자열), `UrgentAlert`.
- `data_adapter.py`가 현재 데이터 소스(CSV `reports.data_access.DataStore`)를 이 스키마로 변환한다.
  저장소가 나중에 진짜 DB로 바뀌어도 이 어댑터만 교체하면 파이프라인/스키마는 그대로다.

## 10. 실행 방법

```bash
# 카드 생성 + 콘솔 출력 + JSON 로그 저장
python -m coaching.run --team 사업부 --start 2026-06-08 --end 2026-06-21

# LLM 없이(오프라인, API 비용 없음) 코드 템플릿으로 서술
python -m coaching.run --team 사업부 --start 2026-06-08 --end 2026-06-21 --no-llm

# 이미 만든 JSON 결과를 재계산 없이 Slack DM으로만 재발송
python -m slack_app.send_coaching_cards --from-json output/coaching_사업부_....json

# 파이프라인을 새로 돌려서 바로 Slack 발송
python -m slack_app.send_team_coaching --team 사업부 --start ... --end ...

# 전체 셀프테스트
python -m coaching.selftest
```

## 11. Slack 연동 (`slack_app/`)

- `home_view.py`의 `build_coaching_cards_blocks`/`build_urgent_alert_blocks`가 Block Kit을 만든다.
  Slack 메시지는 항상 세로로만 쌓여서(가로 배치 불가) 카드를 나란히 보여줄 수 없다 — 대신
  레거시 `attachments` API의 색상 바로 확신도를 구분한다(초록=high, 주황=medium, 빨강=urgent).
  채택/기각 버튼은 붙어 있지만, 클릭을 받는 인터랙티비티 백엔드(별도 엔드포인트 + 공개 URL +
  Slack 앱 설정)가 아직 없어서 반응하지 않는다 — 의도적으로 다음 단계로 미뤄둔 것.
- `send_coaching_cards.py`의 `send_coaching_result()`가 발송 로직 본체이고, `send_team_coaching.py`
  (생성+발송)와 `send_coaching_cards.py`의 CLI(`--from-json`, 발송만)가 이걸 재사용한다.

## 12. FastAPI (`api.py`)

```
POST /coaching-cards/generate         팀·기간 카드 생성(배치, 격주 실행)
GET  /coaching-cards?manager_id=      해당 매니저의 카드 (본인만, 대상자 본인은 조회 불가)
POST /coaching-cards/{card_id}/action 채택/기각 기록
GET  /urgent-alerts?manager_id=       긴급 사안
```

모든 엔드포인트가 신원(`X-User-Id` 헤더 — 데모용 스텁, 실서비스는 JWT/세션으로 교체 필요)을
**필수**로 요구하는 fail-closed 구조다. 초기엔 "헤더가 있고 틀릴 때만" 거부하는 fail-open이었는데
자동 보안 리뷰에서 발견돼 고쳤다 — 헤더 자체가 없으면 그냥 통과되는 구멍이었다.

| `coaching/selftest.py` | 시나리오 A/E/F/G/H/I + API 스모크 테스트. 회귀 확인용, 매 변경 후 실행 |
| `coaching/scenario_validation.py` | 10개 시나리오(진짜 신호 3 + 디코이 7)로 선별 정확도 검증. `--slack`으로 결과 발송 가능 |
| `coaching/scenario_bulk.py` | scenario_validation의 구조를 여러 "사이클"(독립된 가짜 팀)로 반복해, 다른 어휘에도 로직이 일반화되는지 + 실제 LLM 서술 다양성을 한 번에 확인 |

이 세 도구로 이번 구현 과정에서 실제 버그를 여러 번 찾아 고쳤다(§3-1, §7, §8 참고). 특히
**넓은 기간(수개월)을 한 번에 조회하면, 격주(14일) 단위로는 안 보이던 우연한 어휘 겹침이 훨씬 잘
드러난다**는 걸 실측으로 확인했다 — 실사용에서는 항상 격주 단위로 조회할 것.

## 14. 알려진 한계 / 다음 단계

- 미인지 성과 카드 전용 톤 프롬프트 (§8) — 보류 중.
- Slack 채택/기각 버튼 인터랙티비티 — 백엔드 엔드포인트 미구현.
- 의존 병목의 "대상 토큰" 어휘 기반 군집화 — 근본적으로 완벽할 수 없는 휴리스틱(§3-1). 표현이
  많이 다른 진짜 병목을 놓치거나(과소 병합), 생각지 못한 단어로 무관한 건이 묶일 수 있다(과잉 병합).
  원 명세는 이 부분을 LLM 의미 기반 정규화로 설계했으나, recall 문제로 코드 결정론으로 바꾼
  트레이드오프다(§1).
- 채택률보정 — 실제 채택/기각 이력이 쌓여야 의미가 생기는 항목인데, 지금 `CardStore`는 이 집계를
  갖고 있지 않다.
- 저장소가 인메모리(`CardStore`) — 명세는 PostgreSQL을 가정. 실 서비스 전환 시 이 계층만 교체.
